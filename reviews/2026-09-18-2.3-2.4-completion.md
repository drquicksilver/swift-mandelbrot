## Summary

All three findings from the 2.4 follow-up are fixed, with tests that would have caught
them. `1166035` goes further and solves the sizing problem the first review raised: a
zoom-out rung now costs about the same on a phone as on a Mac. The 2.3 ceiling is sound,
and its exactness argument holds.

One medium finding remains, and it is a consequence of the new ceiling. **Lowering the
iteration limit recolours every resident record and cancels the worker.** The ceiling now
lowers the limit on every settle at depth, where the recolour provably changes nothing.
On a zoom-out it changes something, but almost all of the work is either unnecessary or
spent on tiles that are no longer on screen. Three low findings follow it.

## Good

- **Deferral is tied to the budget.** `deferredCoverage` records the band a key came
  from, and `restoreDeferredCoverage` (`TileStore.swift:488`) returns keys as soon as a
  tile fits both the resident limit and the coverage reservation. That is the fix the
  follow-up asked for, not a workaround.
- **The root is never deferred, and makes room.** `makeCoverageRoom` discards strictly
  lower-priority coverage, farthest first, and a root may displace earlier footprints.
  The `precondition` at `TileStore.swift:445` states the invariant plainly.
- **Root retention is bounded, and the test asserts the consequence.**
  `checkRootCoverageBounded` pans 32 view-widths through empty space at a 24 MiB budget
  and requires `nearCoverageCount > 0` — the crowding-out symptom from finding 3, not
  just a record count.
- **The ladder is sized rather than capped.** Each offset takes the finest level that
  fits a few tiles, so a rung costs ~4 tiles on any screen, paid for in resolution
  (1/8–1/16 rather than the spec's 1/4). Clamping projections at
  `Viewport.minimumLogScale` is a good catch on its own: the root footprint was being
  projected past any reachable zoom-out, planning 6–12 cells on a tall phone.
- **The test gaps from the first review are closed.** Realistic device budgets under a
  watchdog, zoom-out quality against each offset's planned level, cold-jump latency with
  coverage on and off alternating in one process (~1% cost), and main-thread p95 while
  moving at 1e1000 (update 0.49 ms, plan 0.37 ms). The numbers are in `Performance.md`.
- **The 2.3 ceiling is exact, and tested as such.** With the highest escaped count below
  a quarter of the limit, no escaped pixel crosses into capped and capped pixels stay
  capped, so the picture cannot change; the test compares against a fresh render.
  `max(1, multiplier)` so a reduced detail setting cannot starve the counts that release
  the ceiling — a subtle trap, handled.
- **Recolour-on-raise is correct given the shader.** `colourSamples` uses the limit only
  for `raw.x >= settings.limit`, and palette phase comes from raw counts, so only records
  holding counts at or above the old limit can change. Both branches are tested.
- **`isPlaceholder` now requires `cappedPixels > 0`.** A tile with nothing capped is
  exact at any higher limit and should not be treated as a stand-in. Correct tightening.

## Findings

### 1. Lowering the limit recolours the whole cache and cancels the worker — medium *(reasoned)*

`TileStore.swift:327`:

```swift
if self.colouring != colouring || iterations < previousLimit || raiseRevealsCounts {
```

The raise side is data-driven (`raiseRevealsCounts`, line 323). The decrease side is
direction-driven: any lowering sets `needsRecolour`, bumps `generation` and cancels the
worker. `recolour` then rebuilds `Array(records.values) + fallback` in full
(`TileStore.swift:757`), and the worker runs it *before* any tile work resumes
(`TileStore.swift:822`), so refinement stalls and whatever tile was in flight — at depth,
possibly seconds of perturbation work — is discarded.

A record only changes colour when it holds an escaped count at or above the new limit.
That gives two cases.

**The ceiling settle: entirely unnecessary.** At 1e1000 the ceiling lowers 266,000 →
5,600 with a highest escaped count of 2,707. Nothing holds a count ≥ 5,600, so by the
same argument `89294f6` uses to skip raises, no record changes colour. This is new
behaviour from that commit: before the ceiling existed the limit only fell when the user
zoomed out; it now fires on every settle at depth.

**The zoom-out: mostly unnecessary, and the rest is invisible.** Zooming out from depth
leaves a cache holding deep tiles computed at the old high limit, which can hold counts
above the new limit and genuinely need recolouring — but those are off-screen and first
in line for eviction. The tiles actually on screen are the coarse ones being zoomed into,
whose counts sit far below the new limit and do not change at all. So the work splits
into "necessary, for tiles nobody is looking at" and "unnecessary, for the tiles on
screen".

Note this means a symmetric predicate alone would *not* skip the zoom-out case: one
high-count record is enough to trigger it. The deeper problem is that the decision is
all-or-nothing across the cache.

**Frequency.** `shouldLower` needs a 10% drop, and `updateDepth` defers 300 ms and skips
while interacting or in motion, so a smooth pinch-out costs one lowering when it stops.
Repeated discrete zoom-outs trip it about every 3 levels between 1e3 and 1e30 — the same
cadence `Performance.md` quotes for the raises this commit set out to stop — and about
every 330 levels at 1e1000.

**Cost.** Not measured; this is arithmetic. Each record costs a fresh 266 KB colour
texture and a `gpu.colour` dispatch, and `submit` awaits completion per call, so these are
sequential round trips rather than one batched pass. A full Mac cache is order 300
records plus ~100 parent mip rebuilds; at 0.1–0.3 ms per round trip that is tens to low
hundreds of milliseconds with refinement stalled. Peak colour-texture memory doubles,
which is budgeted for ("reserve a third for transactional recolouring").

**Resolution.**

1. **Recolour per record**, not per cache: skip any record whose `maximumEscaped` is
   below `min(previousLimit, iterations)`. `recolour` already loops record by record, so
   this is a filter on that loop. This is the fix for the zoom-out case and makes the
   raise path cheaper than its current all-or-nothing form.
2. **Gate the decision with the same predicate, symmetrically**, replacing
   `iterations < previousLimit`. That makes the ceiling settle a no-op.
3. **Reconsider the `generation` bump and worker cancel on a decrease.** Nothing needs
   resampling when the limit falls — that is the commit's own point — so the cancel
   exists only to serialise against the recolour. With (1), in-flight deep work could
   survive it.

`checkIterationReuse` passes unchanged under all three: its 400 → 100 decrease has real
counts in that range and still recolours.

### 2. Deferred coverage only retries when something drives the worker — low–medium *(reasoned)*

`restoreDeferredCoverage` is called from `startWorker` (`TileStore.swift:799`) and the
worker loop (`:824`). But `update` returns early on an unchanged demand
(`TileStore.swift:242`) before reaching `startWorker`, so a rested view whose memory eases
— `retireFallback` dropping fade-retained fallback, say — will not retry until the next
demand change. `checkCoverageDeferralRecovers` relieves pressure via `retryFailedWork()`,
which the app never calls, so the test does not cover the app's own wake-up path.

**Fix:** call `restoreDeferredCoverage` where memory actually eases — after `evict` and
after `retireFallback` — and have the test relieve pressure without calling
`retryFailedWork`.

### 3. `precondition` in `deferCoverage` turns a future slip into a crash — low

`TileStore.swift:445` is a true invariant today: every caller filters the root. But
preconditions stay live in release builds, so a later change that routes a root key there
gives the user a crash rather than a slightly worse picture. An early return plus a
counter would fail the diagnostics just as loudly.

### 4. Two documentation gaps — low

- When `makeCoverageRoom` cannot fit a root, the worker computes it anyway, so resident
  bytes can exceed `residentLimit` by one root tile. That is the right trade, but the
  plan's Storage bullet states the limit without the exception.
- `Performance.md`'s coverage table reads "—" for sparse offsets on both shallow rows,
  while the run prints a selected offset-15 rung in both cases.

## Tests to add

1. **The ceiling settle recolours nothing.** `checkObservedCeiling` already settles a deep
   view; assert `statistics.recolours` is unchanged across the lowering. This pins
   finding 1's main case and is the assertion whose absence let it through.
2. **A zoom-out from depth recolours a bounded number of records.** After the per-record
   change, assert that the count of recoloured records matches those holding counts at or
   above the new limit, rather than the whole cache.
3. **Deferral recovers through the app's own path.** Relieve pressure without calling
   `retryFailedWork`, and assert deferred coverage still returns.

## Suggested order

1. Per-record recolour and the symmetric gate (finding 1, resolutions 1–2), with tests 1
   and 2. This is the user-visible one: it removes a stall that now fires on every settle
   at depth.
2. Revisit the worker cancel on a decrease (finding 1, resolution 3).
3. Retry deferred coverage where memory eases (finding 2), with test 3.
4. Findings 3 and 4 alongside whatever next touches those lines.
