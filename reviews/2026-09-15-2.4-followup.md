# Follow-up review: 2.4 coverage hardening

- **Commit:** `428b893` "Harden coverage cache under pressure", on `main` (2026-09-15).
- **Follows:** `reviews/2026-09-15-2.4-coverage-pyramid.md`.
- **Method:** I read the diff and `TileStore.swift` at HEAD. I did not build or run anything. All three findings come from following the code logic and have not been reproduced.

## Summary

The hardening commit fixes the main problems from the 2.4 review:
- the worker can no longer pick the same key forever;
- coverage has a byte reservation, and the level-of-detail loop leaves room for the root;
- the cap keeps root, then near groups from j = 1, then sparse;
- lookups go through a small index;
- coverage uses its own level's iteration estimate and is never extended;
- the `TileGrid.visible` tile-count check now divides instead of multiplying, so it can't overflow.

Three medium problems remain. Each can leave the "never undrawn" guarantee weaker than it looks: deferred keys are never retried, the root can be deferred, and root-level tiles are never removed.

---

## 1. Deferred coverage is never retried — medium
When a coverage key is skipped for lack of budget (the worker's skip branch) or trimmed (`trimCoverageToReservation`), `deferCoverage` puts it in `deferredCoverage`. In `configureCoverage` the deferred set is only ever narrowed:

```swift
deferredCoverage = deferredCoverage.intersection(selected)
coverage = selected.subtracting(deferredCoverage)
```

So a key only leaves `deferredCoverage` once it drops out of the plan entirely. While the view stays in the same area, deferred keys stay deferred, even after memory frees up: after evictions, when visible demand shrinks, or when the reservation grows. Coverage gaps created under momentary pressure can therefore persist for as long as the user keeps looking at that area.

**Fix:**
- Tie deferral to the budget, not just the plan. For example, clear `deferredCoverage` (or the entries that now fit) whenever `coverageBytes + tileCost <= coverageReservation` and `residentBytes + tileCost <= residentLimit`: after `evict`, after a record is removed, and when `needed` shrinks.
- Alternatively, record the generation or tick at which a key was deferred and retry it with a backoff.
- Test: build pressure so that coverage is deferred, then relieve it (shrink the view or raise the budget). Assert that all planned coverage is eventually computed.

## 2. The "mandatory" root can be deferred — medium
Root coverage is described as mandatory, and the level-of-detail loop reserves room for it (`needed.count * tileCost + rootReservation > residentLimit`). But the worker's skip branch defers **any** coverage key, root included:

```swift
if !self.needed.contains(key) && self.residentBytes + self.tileCost > self.residentLimit {
  if self.coverage.contains(key) {
    self.deferCoverage(key)
  } ...
```

Coverage may take all the bytes left after `needed` (`coverageReservation` is up to 30 MiB), and `trimCoverageToReservation` only enforces that reservation. It never makes room for a *new* root tile. So after a pan, or once the root projection moves to a new cell, a newly needed root cell can find resident memory full of near and sparse coverage and be deferred. Under finding 1 it then stays deferred, and a long zoom-out over that area has no root to fall back on.

**Fix:**
- Never defer a key at `minimumLevel`.
- When a root key doesn't fit, trim near and sparse coverage from the far end (coarsest sparse first, then the highest near offsets) until it does, then compute it.
- Test: fill resident memory with near and sparse coverage, pan so the root projection needs a new cell, and assert that the root tile is computed and nothing near-level is deferred beyond what the trim required.

## 3. Root-level tiles are never removed — medium–low
Three things combine:
- `evict` never removes level −2 records (`&& $0.key.level != minimumLevel`, `TileStore.swift:457`);
- `trimCoverageToReservation` only trims levels above −2 (`$0.key.level > minimumLevel`, line 343);
- `configureCoverage` adds every resident level −2 record to the coverage set on every update (line 314), so each one counts against the coverage capacity.

So every root tile computed since the last re-anchor stays resident for good.

Consequences:
- Root-level tiles fill the selected set, so `selected.count >= coverageTileCapacity` is reached before the near groups, which are dropped. That's the coverage that serves the everyday zoom-out.
- `coverageBytes` can exceed the reservation with nothing left to trim, and resident memory can exceed `residentLimit`, because `evict` can't remove them either.
- Panning through empty space at shallow zoom keeps creating new level −2 tiles, so memory grows without limit until gentle bounds (2.5) restrict panning.

**Fix:**
- Keep the root cells the current root projection needs, plus the cells kept from the previous projection while replacements are pending (the existing hole-avoidance intent). Also keep a small LRU set, for example up to 9 cells.
- Let older level −2 records become ordinary LRU entries: evictable, and not counted as coverage.
- Test: pan a shallow view in a long straight line through empty space and assert that the number of level −2 records and `coverageBytes` stay bounded, and that near coverage is still selected.

---

## Suggested order
1. Never defer the root, and make room for it by trimming (finding 2).
2. Bound root-level records (finding 3).
3. Retry deferred coverage when the budget eases (finding 1).

Each needs its own regression test, run with a timeout so a future worker stall fails the suite rather than hanging it.
