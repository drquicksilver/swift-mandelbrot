## Summary

This is careful, well-judged work. The plan is a good piece of triage in its own right: it
takes the overlap of two independent audits as settled, and it separates what needs no
design from what does, so six stages could land in an hour without deciding anything
that belongs to you. The commit messages and the status section are unusually honest
about departures from the plan. Examples: ⌘? belongs to the system, the double-click
risk was reasoned rather than reproduced, and the failures predate 2.12, which I
confirmed.

One finding needs fixing before this ships. **Stage 5 took the arrow keys and `?` away
from the iPad.** The fix for Mac text fields removed them from the menu, and on iPadOS
the menu was the only thing that bound them. Help still lists them when a keyboard is
attached. Two findings are medium: the menu bar now observes the whole model, which
publishes on every frame of a pan; and the new error translation sorts errors by
substring, which labels some failures wrongly. Everything else is low: copy, dead code
and tests that depend on the locale.

## Good

- **The plan is the right shape.** "What needs designing first" keeps the P0 panel
  scaffold, and the items only that design can settle (Escape, Cancel and default
  buttons, sheet sizing, section headers), out of the mechanical stages. That avoids
  doing them twice, and the status section lists what was noticed and deliberately
  deferred.
- **`ZoomFormat` computes from `logScale`, not from `pow(2, logScale)`.** Beyond 2¹⁰²⁴ the
  exponent branch never goes near `inf`. It handles rounding a mantissa up into the next
  exponent (`9.97e20` → `1.0e21×`), and its tests pin the locale. It fixes the audit's
  `2.0000000000000004e9×` at the source, and the centre stays copyable where precision
  matters.
- **`ValueSlider`/`ValueStepper` are small and correct.** The bounds are formatted the
  same way as the value. The stepper clamps typed input on the Mac, and speaks units the
  way a person would ("12 seconds", "1.5×"). Six ad-hoc treatments now collapse into two.
- **Commands are disabled while a sheet is up.** The status note records why: ⌘J
  reached the view behind the movie sheet. `canPerform` puts that rule in one place, and
  the toolbar's Upright uses the same rule.
- **The file-size estimate was recalibrated from measurements.** Five measured
  renders give a per-second constant instead of a guess. The test pins the audit's own
  case (10.8 MB) to within a factor of two.
- **`DoubleClick` states its rule and applies it to both surfaces.** It requires two
  presses that were both clicks, within 5 pt of each other, and the companion gets the
  same treatment as the main view.
- **Reduce Motion is handled with care.** It turns off flings, snaps, the upright spring,
  refinement fades and place travel. The fade change keeps the store's record lifetime
  unchanged, and the comment says so, which heads off the obvious worry.
- **The copy matches the glossary.** Input words are written per platform as whole
  sentences rather than spliced, so each can be translated whole, and `Glossary.md`
  says why.
- **The stale 2.11 test was fixed properly** (`ce720d2`), by deriving the expected
  density from the log-space fit rather than loosening the bounds.
- **`a88bc84` is what it says.** Sorted, the two versions of `project.pbxproj` are
  identical; only the order changed.
- **The Places button comment was corrected within the series.** Stage 2's comment
  argued for borderless buttons while the Mac used bordered; stage 6 rewrote it to match
  the code.

## Findings

### 1. The iPad lost its arrow keys and `?` — high *(reasoned)*

`6a05eda` made `ExplorerCommand.bindsInMenu` false for every command without ⌘: the
four arrows, and `.help`. `ExplorerCommands.item(_:)` now lists those commands without a
`keyboardShortcut`. On the Mac that is the intent, because `MacInputView.keyDown` handles
them through `ExplorerCommand.matching`.

But `.commands { ExplorerCommands() }` in `MandelbrotApp` is not platform-conditioned. On
iPadOS (`TARGETED_DEVICE_FAMILY = "1,2"`) a Commands menu's shortcuts *are* the
hardware-keyboard key commands, and the iOS side has no other key path: there is no
`onKeyPress`, `UIKeyCommand` or `pressesBegan` in the target. So on an iPad with a
keyboard:

- ← → ↑ ↓ no longer move the view, and `?` no longer opens Controls.
- `HelpView` still shows the Keyboard section when `GCKeyboard.coalesced != nil`,
  listing those keys, so the app documents shortcuts that do nothing.

The text-field problem that motivated the change is real, but it is a Mac problem.

**Fix.** Keep binding the bare keys in the menu on iOS: `bindsInMenu` can return `true`
under `#if os(iOS)`. I believe the text-field conflict does not arise there in the same
way, because since iPadOS 15 text editing takes arrow keys ahead of key commands unless
a command asks for priority. That is worth a quick check with a sheet's field focused. Or add an `.onKeyPress`
handler to the iOS canvas that mirrors the Mac's `matching`. Either way, a test like
TileDiagnostics' "Help command missing" check, asserting that every command listed in
Help has a live binding on each platform, would have caught this.

### 2. The menu bar re-evaluates on every frame of a pan — medium *(reasoned)*

`826d0c1` changed `@FocusedValue(\.explorer)` to `@FocusedObject`, so that menu items
could follow `canGoBack` and friends. That works, but `ExplorerModel` is one
`ObservableObject` with `@Published var viewport`, `juliaC`, `progress` and `image`,
among others. Every pan, zoom and fling frame, and on the Mac every mouse move while
the crosshair follows the pointer, now invalidates `ExplorerCommands.body`. That body
rebuilds the Settings group, the eight-group Explore menu, Help and the Debug menu.

I have not measured it. SwiftUI may coalesce these updates into one per run-loop turn,
and AppKit may only diff the `NSMenu`. But this is the app's top priority, smooth pan
and zoom, and a per-frame menu rebuild is the kind of cost that does not show up in
the renderer benchmarks. The window subtitle added in stage 5 is also per-frame, but it
is a single string and cheap.

**Fix.** Measure it first: an Instruments *SwiftUI* trace over a fling, counting body
evaluations of `ExplorerCommands`. If it shows, give the menu its own small
`ObservableObject` that holds only what the menu reads (`canGoBack`, `canGoForward`,
`isRotated`, `showJulia`, `isPresentingSheet`). Have the model update it only when those
values change, and keep `@FocusedValue` for the model itself.

For contrast, I did measure one per-frame cost that looked similar. The canvas's new
accessibility value, `location.suggestedName`, runs on every `ViewerView` body. It
costs about 0.1 ms per call in release, both at 4,000× and at 1e100×, which is
negligible, so it is not a finding.

### 3. Error messages are chosen by substring, and some are wrong — medium

`MovieRenderer.message(for:)` is the right idea, but the classification cannot work
from the information it receives:

- Every writer failure is flattened into `GPUFailure(String)` at the throw site, for
  example `GPUFailure(writer.error.map { String(describing: $0) } ?? …)`. So the typed
  `NSCocoaErrorDomain` permission branch never sees an `AVAssetWriter` error. A folder
  without write permission that fails inside the writer gets "Check there is room on the
  disk".
- `"The movie writer has no pixel buffers"` (the pool was never created, usually
  because the writer failed to start) contains `"pixel buffers"`, so it becomes "ran out
  of memory. Try a lower resolution".
- `"Could not draw into a movie frame"` and `"No Metal texture cache…"` fall through to
  the disk-space message.
- `PrecisionError` passes through on the grounds that "a journey's own errors are already
  sentences". Four of them are: the two rewritten in stage 3, plus `ZoomPath`'s and the
  sheet's duration message. But `Journey` still throws "A journey needs a positive aspect
  ratio" and "The overview must be no tighter than the suggested shared view", and
  `Viewport`/`DeepNumber` throw "Scale outside [1e-6, 2^13000]" and "Invalid decimal
  coordinate". All of these reach `journeyProblem` through `refreshJourney`, and none is
  localised. They are hard to trigger from the UI today, so this is latent, but "Invalid
  decimal coordinate" is on the audit's list of jargon to retire.
- The commit message says the thrown text "stays for diagnostics", but `message(for:)`
  discards it and nothing logs it. After this change a failed render leaves no trace of
  its cause.

**Fix.** Give movie failures a small typed error at the throw sites, with cases such as
`.gpuUnavailable`, `.writerFailed(underlying: Error)`, `.outOfBuffers` and `.cannotDraw`,
and map those to sentences. Stop matching on text. Keep a whitelist of the
`PrecisionError`s that are copy, or better, give copy its own error type. Log the
underlying error with `Logger` before replacing it with the friendly message.

### 4. Place travel runs on its own 16 ms timer — low *(reasoned)*

`ExplorerModel.travel(to:)` animates by setting `viewport` from a `Task` that sleeps
16 ms per step. Everything else in the app that moves the view does so from the
display-driven motion clock (`advanceMotion`, the GPU canvas's own clock). A sleeping
task drifts against the display: about 60 steps per second, unevenly spaced, even on a
120 Hz screen. For a 0.6–1.6 s move that is visible judder in the one transition both
audits asked for. It also sets the view directly, without `interactionActive`, so every
step asks the tile store for a settled view rather than an interactive one.

**Fix.** Drive travel from the existing motion clock: store the journey, its start time
and duration as motion state, and step it in `advanceMotion`, which already knows how to
stop for a gesture. The cancellation logic can stay as it is.

### 5. The string catalogue will churn between Xcode and `make strings` — low

`tools/update_strings.py` writes `json.dumps(indent=2)`: `"key": value`, with `{}` on
one line. Xcode writes `"key" : value` and expands empty objects. It also keeps keys the
script filters out (`""`, `"24"`, `"· %@"`), and it adds positional forms such as
`"%1$@ · %2$@"`. Opening the project in Xcode at 09:40, a minute after `a88bc84`, has
already rewritten the whole file: `Localizable.xcstrings` is modified in the working
tree, +761 −248, with 250 → 244 keys. I have left that change alone. Every round trip
between the IDE and `make strings` will now rewrite the file in full.

**Fix.** Pick one writer. The simplest is to match Xcode's format in the script: use
`separators=(",", " : ")`, expand empty dicts, and stop dropping the keys Xcode keeps.
Or treat the IDE as the source and use the script only to add missing keys.

### 6. Smaller things — low

- **Travel parts are named by the journey's end, not by their own end.** The
  `Journey.title(of:)` `.travel` case returns "Across to \(label(end))", so a three-part
  journey reads "Out from Seahorse Valley / Across to this view / In to this view". The
  glossary asks for parts to be named by their ends, and the travel part ends at the
  overview above this view, so "Across to the overview" or "Across the set" would match.
- **`label()` recognises overviews by `name == "Overview"`**, a string that
  `Journey.planned` sets four times. A `Location.Role`, or a flag, would survive the
  string ever being localised.
- **"Zoom from The whole set into this view."** The gallery name is capitalised
  mid-sentence, and the test locks it in.
- **`suggestedName` mixes minus signs.** It uses an ASCII `-` for the real part and `−`
  for the imaginary sign ("-0.2 − 0.7i"), whereas `juliaPoint` replaces both. The test
  also asserts the ASCII form.
- **Some tests depend on the host locale.**
  `anUnnamedBookmarkIsNamedForWhereItIs`, `journeysAreDescribedByTheirPlaces`,
  `zoomOfALocationIgnoresItsExactDecimal` and
  `galleryZoomsReadPlainlyUntilTheDigitsStopMeaningAnything` use `.current`, so they
  would fail on a machine set to German. `ZoomFormat` takes a locale, but
  `suggestedName` and `zoomDescription` do not.
- **`ExplorerModel.showDeveloper` is now dead.** Nothing sets it on either platform: the
  Mac opens a window, and iOS uses `AppearanceView`'s own `@State`. The iOS
  `.sheet(isPresented: $model.showDeveloper)` in `ContentView` and its term in
  `isPresentingSheet` can go.
- **Triple clicks now zoom twice.** `DoubleClick.isDouble` tests `clickCount >= 2`
  where the old code tested `== 2`. Quick repeated clicks zooming repeatedly may be what
  you want, but no commit or help line mentions the change.
- **The file-size estimate is a Mac constant used on both platforms.** The comment's five
  measurements were Mac HEVC. The iPhone's encoder may differ, so it is worth one
  measured render before the iPhone sheet shows "About".
- **The companion divider stops following the pointer near its minimum.** The panel's
  `max(220, …)` floor overrides the dragged fraction whenever fraction × width is under
  220 pt. Below about 1,470 pt of window width, the line stops following a drag toward
  the edge before the 15% limit, while the stored fraction keeps changing. Clamp the
  fraction to `220 / width` as well.
