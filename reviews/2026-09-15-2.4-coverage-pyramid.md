# Code review: 2.4 coverage pyramid

- **Commit:** `1fac0b0` "Add bounded zoom-out coverage pyramid", on `main` (2026-09-15, 09:27).
- **Spec:** the 2.4 text committed in `aa1b5b7`.
- **Method:** I read the diff and the relevant files at HEAD (`TileStore.swift`, `TileCompositor.swift`, `TileGrid.swift` and the diagnostics). I did not build or run anything. Findings marked *(reasoned)* come from following the code logic and have not been reproduced.

## Summary

The design is right, and several parts are well done. However, there's a likely **main-thread hang** when the memory budget is nearly full. Coverage isn't part of the memory budget. The 40-tile cap throws away the most useful coverage. Per-frame main-thread work grew and wasn't re-measured. Several parts of the spec were dropped, while `plan.md` now calls 2.4 "Completed". Fix findings 1 and 2 before this build is used on a phone.

## Good

- **Projecting the zoomed-out view.** `TileGrid.visible(…, zoomOut:)` projects the future zoomed-out view in one place, for both the ordinary and the deep coordinate paths, with a unit test (`projectedZoomOutCoverageStaysCoarse`).
- **Composition.** Coverage is looked up by position, so it isn't limited by the 62-level ancestor walk.
- **Re-anchoring.** Old-anchor coverage is kept as fallback until the new root tile is ready, so re-anchoring doesn't open holes.
- **Protection.** Coverage is protected from LRU eviction and isn't invalidated by iteration changes.
- **The long zoom-out test.** A 2¹²⁸ zoom-out straight after a cold jump to 1e1000, checked with the magenta sentinel, is exactly the right test.

## Findings

### 1. The worker can spin forever on the main thread — high *(reasoned)*
`TileStore.swift:529–540`:

```swift
while !Task.isCancelled, self.generation == generation, let key = self.nextKey() {
  ...
  self.evict(reserving: self.tileCost)
  if !self.needed.contains(key) && self.residentBytes + self.tileCost > self.residentLimit {
    self.prefetch.remove(key)
    continue
  }
```

Coverage keys aren't in `needed`. When the budget is full, a pending coverage key reaches the skip branch. `prefetch.remove(key)` does nothing to it, so the key stays in `coverage`, `nearCoverage` or `sparseCoverage`. `nextKey()` then returns the same key, and there's no `await` between iterations. The `@MainActor` worker therefore loops forever, and the UI freezes.

**When it happens:** the tiles on screen plus the finished coverage tiles fill `residentLimit` while another coverage tile is still pending.

**Why ordinary use hits it:**
- With `ceil(lod)`, the number of visible tiles swings by up to 4× within each level as you zoom.
- The loop that lowers resolution when over budget (line 242) only counts `needed`, so demand hovers just under the limit.
- On iPhone, `residentLimit` works out to roughly 85–120 tiles of about 0.8 MB each (fewer at depth, where reference and BLA memory are reserved). In landscape, the visible tiles plus up to 40 coverage tiles land squarely in that range. A full-screen Retina Mac can get there too.

**Why the tests miss it:** the diagnostics use 256×192 views, which never come near the budget.

**Fix:** every skip must make progress. Drop the key from all coverage sets (trimming from the far end, see finding 2), or mark it deferred until the budget changes. Add the regression test described in "Tests to add".

### 2. Coverage isn't part of the memory budget — high
- **Only a count cap:** the spec asked for a reserved budget. The implementation has a *count* cap (`coverageTileLimit = 40`) but reserves no bytes.
- **Resolution ignores coverage:** the loop that lowers resolution to fit the budget (`while needed.count * tileCost > residentLimit`, line 242) doesn't include coverage.
- **Scheduling ignores the budget:** `nextKey` (lines 366–370) lets any pending root, near or sparse coverage through, whatever the budget. So the resident set can exceed the budget on iPhone.
- **No trimming under pressure:** the spec's rule (trim from the far end and thin the sparse levels, keeping the root and the first near levels to the end) isn't implemented.
- **Unused counter:** `coverageBytes` (line 121) is computed but never used.

**Fix:** reserve `coverageTileLimit × tileCost`, or the actual coverage bytes, from `residentLimit` before choosing the level. When over budget, trim coverage in the spec's order instead of exceeding the budget or skipping.

### 3. The cap keeps the least useful coverage — medium
`configureCoverage` trims to 40 tiles with `add()`, which sorts by **ascending level (coarsest first)**. So when the cap binds, it keeps the farthest near levels and drops j = 1–4, the levels that serve the everyday 2–16× pinch-out. The sparse levels are only added if room is left, which on real screens it isn't.

**The cap always binds on real screens:**
- At zoom-out j, coverage level L − j − 2 spans about a quarter of the view's width in tiles, plus boundary tiles.
- That's **6–24 tiles per level** on an iPhone or a Mac. (The planning estimate of 1–4 was wrong.)
- Eight near levels alone exceed 40.

**The result:**
- A 2–16× zoom-out shows edges from very coarse levels, around 128× blur, rather than quarter resolution.
- A long zoom-out falls back on the root tile alone.
- The 256×192 tests never reach the cap.

**Fix:** trim in priority order: root, then near j = 1…8 in order, then sparse in order. Compute order can stay coarse-first within the selected set. Also size the cap from the screen (levels × tiles per level), and/or use coarser tiles (L − j − 3) for j ≥ 5 and the sparse levels.

### 4. Per-frame work on the main thread grew — medium
- **In the compositor:** `bestAvailable` now builds `(Array(records.values) + fallback)` and filters it on **every call**. The compositor calls it about three times per visible tile per frame, so the cost is visible tiles × resident records per frame, with an array allocation each time. On a Mac that can be hundreds × hundreds.
- **In `configureCoverage`:** it runs on every update that isn't skipped (every frame while moving). That's about 21 `grid.visible` projections (BigInt subtraction and conversion at depth), sorting a few hundred keys, and re-marking `isCoverage` on every record.
- **Not re-measured:** the earlier CPU preparation figure (0.02 ms p95) predates this commit.

**Fix:**
- Keep a small index of coverage records (at most 40, plus coverage fallback) ordered by level, and look them up directly.
- Compute the anchor-relative viewport centre once per update and reuse it for every projection.
- Re-measure `preparationP95MS` and `updateMS` at 1e1000 **while moving**, and record them in `Performance.md`.

### 5. Coverage is sampled and extended at the full limit — low–medium
The worker samples every tile at `self.iterations` (line 532), and `needsSampling` re-queues any coverage tile with capped pixels whenever the limit rises. The spec said coverage is a placeholder that is never extended.
- The root is cheap even so: only about 1% of a level −2 tile is inside the set.
- Near and sparse coverage close to a minibrot will repeat the expensive inside-the-set work after every rise, competing with zoom-in prefetch.

**Fix:** sample coverage at the depth estimate for its own level (`IterationPolicy.estimate(logScale: Double(level))`), and exclude coverage from extension when the limit rises.

### 6. The plan says "Completed" but parts of the spec were dropped — low
The 2.4 text in `plan.md` was replaced by a summary that doesn't mention these parts of the spec:
- memory-pressure trimming (finding 2);
- never extending coverage when the iteration limit changes (finding 5);
- zoom-out prefetch;
- the test that cold-jump time until visible tiles are ready is unchanged;
- the root under a fixed world anchor. It now sits under the current anchor and is recomputed after re-anchoring. That's cheap and acceptable, but it's a deviation.

Some of these may be deliberate. The plan should list them as deviations, to the standard `Implementation.md` holds itself to elsewhere.

The new text also says "axis-aligned future viewport". That's fine until rotation (2.5) lands, but 2.5 should gain a note that the coverage projection must handle a rotated view.

### 7. Minor
- `TileStore.swift:252`: the comment "Zoom-out's next level is already protected in the ancestor chain" is now wrong.
- `coverageBytes` is unused (see finding 2).

## Tests to add
1. **Realistic sizes and budgets, with a timeout:**
   - iPhone-sized (2622×1206) at 150 MiB and Mac-sized (3456×2234) at 500 MiB;
   - sweep the zoom continuously through several levels, shallow and at 1e1000;
   - assert the worker always makes progress, resident bytes stay within budget, and coverage stays within its reservation.

   This catches findings 1–3.
2. **Quality for moderate zoom-outs:** after the pyramid is ready, zoom out 2×, 4× and 16×. Assert no sentinel pixels, and that each cell is served from level L − j − 2 or finer.
3. **Cold-jump latency:** time until visible tiles are ready after a cold jump to 1e100 and 1e1000, compared with the numbers from before 2.4. Coverage must not delay the visible view.
4. **Main-thread cost:** preparation and update p95 at 1e1000 during a 120-frame pan and zoom, with a threshold.

## Suggested order
1. Make the worker always make progress (finding 1) and add test 1.
2. Put coverage in the budget and trim in priority order (findings 2 and 3).
3. Index coverage and cache the projections; re-measure (finding 4, test 4).
4. Sample coverage at a level-appropriate limit and don't extend it (finding 5).
5. Update the 2.4 text in `plan.md` to list what's done and what deviates, and add the rotation note to 2.5 (finding 6).
