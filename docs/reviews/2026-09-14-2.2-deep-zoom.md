# Code review: 2.2 deep zoom (precision library, perturbation, BLA)

- **Branch:** `main`, reviewed at `eafab88` (2026-09-14, about 15:15).
- **Commits:** `269be3d` (library spike and fixed-point coordinates), `9609e31` (GPU perturbation), `eafab88` (BLA and shared references).
- **Method:** I read the code at HEAD and the diffs, and checked the committed evidence. I did not run `make test`. Findings marked *(reasoned)* come from following the code logic and have not been reproduced.

## Overall

This is a real deep-zoom engine, built carefully:
- The camera stores its centre in fixed point and its zoom as a logarithm.
- Perturbation runs in FloatFloat, with a separate exponent for each component. The comment explaining why a shared exponent would lose tiny imaginary parts is exactly the right insight.
- It uses Zhuoran's rebasing, Pauldelbrot glitch recovery and a BLA table.
- It's validated against an **independent Python Decimal oracle** at 1e50, 1e200 and 1e1000, with BLA both on and off.
- Credits for the algorithms are given, and no source code was copied.

The headline numbers are credible: at 1e1000, 400 → 141 ms end to end, with GPU time down 7.9×.

The main weakness is that **every numerical test and benchmark uses one very convenient location: c = i.** c = i is a Misiurewicz point. Its reference orbit never escapes and never comes near 0, the evidence shows zero glitches, and it needs only about 2,700 iterations at 1e1000. The places people actually zoom to are next to minibrots. There, orbits pass near 0 every period, iteration counts run into the tens or hundreds of thousands, and the glitch, reference and cache paths all get stressed. Several findings below would only show up there.

## Findings

### High

**1. The glitch check always pre-empts rebasing** (`Perturbation.metal:63` and `:69`) *(reasoned)*
- **What happens:** the Pauldelbrot test (|z|² < 10⁻⁸·|Z|²) runs *before* the rebase test (|z|² < |δ|²). Whenever the Pauldelbrot condition holds, |δ| = |z − Z| ≥ |Z| − |z| > |z|, so the rebase condition holds too. The pixel is therefore marked as glitched (−3) and sent round another reference pass, in exactly the situation rebasing was designed to handle for free.
- **Why it matters:** near minibrots this will be common. Each glitch costs a whole new CPU reference orbit (see finding 2), and after 16 passes the tile fails with "Perturbation needs more than 16 references". c = i never triggers it, and the one test that does trigger glitches uses a 7×5 view of the whole set.
- **Fix:** test for rebasing first. With Zhuoran rebasing, Pauldelbrot detection is normally unnecessary. Keep it as a diagnostic counter, or only when rebasing is switched off. Add a test near a minibrot that asserts a small number of references.

**2. The reference cache misses on every level change, and turns off entirely at high iteration counts** (`BilinearApproximation.swift:81–103`, `TileStore` tile path)
- **Cause:** entries are matched on exact `(point, iterations, bits)`. A tile's `bits` is `level + 128`, so every zoom level asks for a different key. Once a view spans a few levels, the cache of three entries thrashes. Changing iterations misses as well, even though an orbit computed to N iterations covers any shorter run.
- **The cut-off:** orbits over 4 MiB, about 131,000 iterations at 32 bytes each, are never cached. Past that point every tile, and every glitch pass, recomputes its BigInt orbit.
- **The cost:** the evidence shows about 20 µs per iteration at 1e1000 (102 ms for 5,000). At 100,000 iterations that's about 2 s per tile.
- **Fix:**
  - round `bits` up to a coarse step, such as a multiple of 256, so neighbouring levels share an orbit;
  - on lookup, accept any cached orbit with at least the requested `bits` and `iterations` (fewer iterations means using a prefix);
  - set the size cap from the tile memory budget instead of a fixed 4 MiB.

**3. The iteration caps now block deep zoom in practice** (`ExplorerModel.swift:109`, `AppearanceView.swift:29`, `BenchmarkCLI.swift:22,176`)
- The default is 200 iterations, `⌘]` stops at 65,535, and the Settings stepper only goes from 200 to 10,000. A friend who zooms to 1e1000 near c = i sees solid black until they raise the limit to about 3,000. Near a minibrot, 65,535 won't be enough.
- The 65,535 cap dates from the old 16-bit count buffers, which the GPU path no longer uses.
- **Fix:** lift the caps (float32 smooth counts stay precise enough up to about 10⁶–10⁷), and treat 2.3 (automatic iteration depth, at least the depth-based first guess) as the next item. It is now what decides whether 2.2 is usable at all.

**4. The deep tests don't cover the hard cases or the product's own path**
- **Location:** every deep golden and benchmark uses c = i at 5,000 iterations and 32×24 (see the Overall section).
- **Path:** the numerical goldens exercise the full-frame `--pipeline gpu` path, with endpoint sampling. The product's deep path goes through tiles: a reference per tile, the grid anchor used as reference, `bits` set per level, and the cache. That path only gets structural checks in `TileDiagnostics.checkDeepTiles`: coverage, reuse, memory, and that the image isn't flat.
- **Fix:**
  - a golden next to a minibrot, at 1e50–1e100 so the Decimal oracle stays affordable, with 20,000+ iterations;
  - a deep golden through `--pipeline tiles`, using a version of the oracle that samples pixel centres;
  - a benchmark at the minibrot location alongside c = i.

### Medium

**5. BLA has only one level, so it can never skip more than 32×** (`BilinearApproximation.swift:33–70`)
- Blocks are a fixed 32 steps, aligned to the reference. The 7.9× GPU speed-up is close to that ceiling. The stated reason, "bounds work per GPU operation", doesn't hold: a jump costs one operation whatever its length.
- **Fix:** build the standard merge hierarchy. Combine neighbouring blocks with A = A₂A₁, B = A₂B₁ + B₂ and R = min(R₁, max(0, (R₂ − |B₁|·|δc|)/|A₁|)), and at each step apply the longest block whose radius holds. The table only grows by about 2×.
- **Also:** the radius is very conservative. It uses ε = 2⁻⁴⁴, and a factor |Z|/(2|Z|+1) where the usual formula is about 2ε|Z|: 40× smaller at |Z| = 10. Tune ε against the goldens, which currently show a 0–6×10⁻⁵ error margin.

**6. Arbitrary-precision (BigInt) maths runs every frame on the main thread at depth** *(reasoned)*
- **Where:** `TileCompositor.encode` calls `bestAvailable`, then `fallbackAvailable`, then `TileBounds.relative(to:)`. That's a BigInt subtraction plus conversions to `wide`, for every pair of visible tile and fallback record, every frame. `grid.bounds(key)` recomputes a BigInt offset each time, and the `nextKey` comparator does the same.
- **Why it matters:** at 1e1000 these are numbers of about 3,450 bits, handled at up to 120 Hz on an iPhone 11 Pro.
- **Fix:** when two keys share an `anchorID`, work out their relative position from the integer keys alone, with no BigInt. Only records from an earlier anchor need BigInt. Cache `TileBounds` per key. Then check `updateMS` in the HUD at 1e1000 on the phone.

**7. The reference point can drift far from the tiles** (`TileStore` sets `preferredReference = grid.deepAnchor`) *(reasoned)*
- The grid anchor only moves once tile indices pass 2³⁰. After panning a long way at depth, |δc| becomes large, so every BLA radius collapses to 0 and rebasing becomes frequent. It gets slower gradually, without breaking.
- **Fix:** choose the reference independently of the grid anchor, e.g. the nearest cached reference within a few tiles, otherwise the tile's centre.

**8. After a glitch, the new reference is the lowest-numbered glitched pixel** (`atomic_fetch_min` on the pixel index)
That's the top-left edge of the glitched region, which is often a poor reference for the rest of it. Choose the pixel with the smallest |z|/|Z|, or the centre of the region. This matters less once finding 1 is fixed.

### Low

9. **Renderer thresholds live in three places:** `ExplorerModel` (`logScale > 40`, which also ignores the developer override), `Viewport.recommendedRenderer` (`logScale + log2(px) > 40`), and `TileStore` (`level > 32`, and `> 40` for the override). The second and third agree, since level ≈ logScale + log2(px/256). Put the rule in one function.
10. **`ReferenceOrbitCache` computes inside the actor,** so a cache hit waits behind a miss, and there's nothing to stop two identical requests both computing. That's harmless with one tile worker, but worth fixing before adding more.
11. **Each perturbation call allocates a new 3.2 MB `states` buffer.** Reuse one per worker.
12. **The BigInt MIT notice is still missing from the app.** It only appears in a source comment. It's required before TestFlight or the App Store: add Settings → About → Acknowledgements.
13. **The Boost comparison still can't be reproduced from the repo** (there's no script to fetch Boost), yet `Performance.md` names Boost as the next performance option.
14. **`DeepNumber` right shifts round toward zero for negative values,** because the numbers are stored as sign and magnitude. That's symmetric and harmless with 128 guard bits; add a one-line comment.

## Notes per commit

### `269be3d` Library spike and fixed-point coordinates
A fair comparison, with pinned versions, raw data and honest caveats: fixed point truncates where Boost rounds, and it measures arithmetic rather than a full reference. Vendoring BigInt with its provenance and licence is tidy. See items 12 and 13 above, and my earlier note that a pinned SwiftPM dependency would keep about 3,500 lines of someone else's code out of the diffs employers will read.

### `9609e31` GPU perturbation
The core is sound:
- **Navigation:** fixed-point camera, log zoom, hysteresis when switching precision (promote above 30, demote below 28), and anchored zoom and pan tested at 1e1000 to 10⁻⁹ px.
- **Tiles:** geometry relative to the anchor; tile levels up to 13,000 with ancestor lookups limited to 62 levels.
- **Arithmetic and cancellation:** the extended-exponent maths is careful about the dangerous cases (alignment limits, normalisation), and cancellation reaches the CPU reference work too.

Issues: findings 1, 4, 7 and 8. The pixel-to-coordinate mapping (endpoints) matches its oracle, but it's a second convention alongside the tiles' pixel centres, and it's the only one the deep goldens cover.

### `eafab88` BLA and shared references
- **Good:** BLA is validated both on and off against the independent oracle, counters record iterations actually skipped, and a deliberately upward-rounded δc bound keeps radii safe when values underflow Double. The evidence is honest that the ~102 ms CPU reference now dominates.
- **Issues:** findings 2, 5 and 6.
- **Question:** `ExplorerModel.renderer` forces perturbation above logScale 40 and silently ignores the developer override there. Is that intended?

## Suggested order

1. **Fix the kernel logic:** swap the rebase and glitch checks (1), and add a golden next to a minibrot plus a deep golden through tiles (4).
2. **Make references reusable:** round `bits` up and accept cached orbits with at least the requested bits and iterations (2).
3. **Make deep zoom usable:** lift the iteration caps and implement the 2.3 first guess (3).
4. **Speed:** the BLA hierarchy (5), then measure main-thread BigInt cost on the iPhone and add the same-anchor fast path (6).
5. **Before any TestFlight build:** the licence notice (12).
