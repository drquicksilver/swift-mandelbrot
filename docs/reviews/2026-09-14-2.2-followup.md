## Summary

Every finding from the 2.2 review has been addressed, several better than suggested. The hard minibrot golden (an independent Newton + Decimal oracle) and the tile-path oracle are genuinely hard tests, and the documentation is honest about tolerances and what hasn't been measured.

One new problem is significant. **Automatic iteration depth, as wired up, keeps throwing away the tile cache and making reference orbits expensive.** In normal use, the iteration count changing now discards work more often than anything else. Fix it before the next session on the phone.

## New findings

### 1. Automatic depth keeps throwing away the tile cache — high (`TileStore.swift:172`)
Any change to the iteration count calls `invalidate()`, which clears every cached tile. Old tiles remain on screen as fallback while replacements are computed. Automatic depth now changes the count often:

- **Zooming in:** it rises when the target moves by at least 10% or 200 iterations. Between 1e3 and 1e30, the range most people will explore, that's every **2½–3½ zoom levels**. At 1e9, for example, the count is about 2,600 and rises every 260 iterations, which is every ~3¼ levels. Each rise recomputes all visible tiles and the protected three-level band above them.
- **Zooming out:** *any* decrease is applied once input has been still for 300 ms. Decreases have no size threshold, so a one-level zoom-out followed by a pause wipes the cache. The view you return to is always recomputed from scratch, because its earlier tiles were thrown away by a rise on the way in.

This undoes the tile cache during ordinary exploration, and could reproduce the "gets slow and stays slow" experience for a different reason.

**Suggested fix:**
1. Store the iteration limit in each `TileRecord`.
2. **Decreases:** a tile computed with a higher limit is valid for any lower one. Escaped counts below the new limit are unchanged, and counts at or above it can be coloured as capped (pass the limit to the colour kernel). Nothing needs recomputing.
3. **Increases:** keep the records. Mark them "needs extension", and resume only the capped pixels (the resumable and perturbation state machinery already exists). Until that's built, at least keep the records as fallback and recompute them lazily.
4. Immediately and cheaply: never invalidate on a decrease, and give decreases the same size threshold as increases.
5. Test: zoom in steadily from 1× to 1e30 and back out, and assert how many tiles are recomputed.

### 2. Reference orbit cost grows with the automatic limit — medium-high (`ReferenceOrbit.compute`, `ReferenceOrbitCache`)
The orbit is computed to the full iteration limit before GPU work starts, unless the reference escapes first. At 1e1000 the estimate is about 266,000 iterations. The c = i reference never escapes, so at the measured ~20 µs per iteration that's about **5 s of BigInt maths before the first deep tile appears**, and longer on the iPhone 11 Pro.

Also, a cached orbit can only serve an equal or *shorter* request. When the limit rises, the whole orbit is recomputed from iteration 0, because the final BigInt state isn't kept.

The tests use fixed iteration counts (5,000 and 60,000), so this interaction isn't measured.

**Suggested fix:**
1. Keep the final BigInt `(x, y)` in `ReferenceOrbit`, so a cached orbit can be *extended* rather than recomputed.
2. Compute the orbit in chunks, just ahead of the iteration reached by the furthest unfinished pixel, rather than to the full limit up front.
3. The 80-per-zoom-level slope in the depth estimate (suggested in the plan) fits minibrots (1e100 needs 22,000–34,000) but is about 100× too high for spirals like c = i. That makes the data-driven half of 2.3 (lowering the limit when the highest escaped count is far below it) worth doing soon.
4. Add a benchmark: a cold 1e1000 view with automatic depth, measuring time to the first deep tile.

### 3. The BLA hierarchy is held back by a compounding margin — medium (`BilinearApproximation.swift:88`)
Each merge multiplies the parent's radius by 1/32, *after* taking the minimum of its children's radii, which were already reduced. So the reduction compounds. A 16,384-step block (nine merges above a 32-step leaf) ends up with a radius 2⁻⁴⁵ times smaller. That explains the final evidence, where the hierarchy is about level with fixed 32-step blocks:

| Location | Fixed 32 | Hierarchy |
|---|---:|---:|
| minibrot, 1e100 | 476.73 ms | 489.47 ms |
| c = i, 1e1000 | 118.66 ms | 112.58 ms |

The margin was tuned so the tile-path minibrot golden passes. That comparison is dominated by chaos at the set boundary: with **BLA off**, the maximum smooth-count error is already 237.96. The margin has been fitted to noise, not to BLA error.

**Suggested fix:**
1. Measure BLA's own error as **BLA on vs BLA off, using the same GPU arithmetic**, at the minibrot and c = i. Everything except the approximation is identical, so the chaos cancels.
2. Choose ε and the margin from that measurement. If a margin is still needed, make it a fixed allowance per jump, not one that compounds with every merge.
3. Make that on-vs-off comparison a strict test. The minibrot tolerances (up to 5% outliers, maximum error below 512) are necessarily too loose to catch subtle BLA regressions.

### 4. The deep anchor still sticks, and the reported slowdown wasn't reproduced — low-medium
`TileGrid.rebase(to: CGPoint)` still has no callers. Once the grid has re-anchored at depth, `deepAnchor` stays set for the rest of the session, keeping the precision it was captured at. The integer-key fast path and the early exit make this mostly harmless:
- tile bounds are cached;
- one precise conversion happens per frame;
- `visible()` still subtracts at the anchor's full precision on each update that isn't skipped.

However, the scenario you actually reported (fine at first, slow after one deep trip, still slow after zooming out) was never reproduced as a test, so it's unconfirmed that it's fixed.

**Suggested fix:**
1. In `TileStore.update`, when `viewport.deepCenter == nil` and `grid.deepAnchor != nil`, call `grid.rebase(to: viewport.center)`.
2. Add a regression test that starts fresh, zooms to 1e12, returns to 1×, and asserts that update time, preparation time and tile work match a fresh session within a small margin.

### 5. Raw samples take more memory — low
The 8-byte sample format makes each tile about 800 KB (8-byte samples plus 4-byte colour, 258² each) instead of about 530 KB. On iPhone that's roughly a third fewer tiles within the 150 MiB budget. That's acceptable. If memory becomes the limit, the correction could be stored as Float16.

### 6. Still no phone measurements
Frame pacing, CPU preparation time and touch feel on the iPhone 11 Pro and iPhone 16 Pro remain unmeasured. The documentation says so clearly. The most useful next piece of evidence is the user repeating the original session on the phone with the HUD on.

## Suggested order

1. **Tile cache and iteration changes (finding 1):** at minimum, no invalidation on a decrease and a threshold for decreases; then per-record limits and extending only capped pixels.
2. **Re-anchor when shallow, and the round-trip regression test (finding 4).** Both are small.
3. **Extendable reference orbits and a cold-deep benchmark (finding 2).**
4. **Measure BLA error on vs off and remove the compounding margin (finding 3).**
5. **Try the original session again on the phone.**
