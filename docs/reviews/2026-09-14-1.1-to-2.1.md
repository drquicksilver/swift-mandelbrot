## New findings, in priority order

### 1. A deep view takes about 1.5 s to appear from cold (`TileStore.nextKey`, worker loop)
`2.1d-cache.json` shows about **1,490 ms** to refine a 256² view at 1e10 with 4,000 iterations. A single full-frame FloatFloat render of the same view would take about 10 ms. That's roughly 150× slower. There are three causes:
- `needed` includes *every* ancestor from level −2 down to the visible level, which is about 37 levels at 1e10.
- `nextKey` orders strictly coarse-first across all levels, so the visible level is computed last.
- Tiles are computed one at a time, each in batches of about 1 ms, with a CPU round trip after each batch.

This will be felt whenever someone jumps to a deep location: bookmarks and share links (2.4), zoom-movie keyframes (2.6), and reset followed by rapid zooming.

Suggested fixes:
- When no cached tile covers the visible level, give it priority over distant ancestors. Keep only a few levels above it in the protected set, and fill in the rest of the chain lazily. Coarse-first is right while zooming continuously, but not after a jump.
- Put several tiles in each command buffer, rather than one tile per batch.
- Choose the batch target by state: about 1 ms while the user is moving, and 4–8 ms at idle. The compositor uses its own queue and needs only about 0.25 ms of GPU time.
- Add a benchmark of "cold deep view to all visible tiles ready" and track it.

### 2. Changing the iteration count blanks the screen at depth, and blocks 2.3 (`TileStore.invalidate`)
`invalidate()` keeps only level −2 root tiles as fallback. In 2.1b it kept all of them. So after an iteration change at 1e10, the view falls back to the root tile magnified 10¹⁰ times, which is a flat colour, for the full cold-refinement time in finding 1. That's a regression from 2.1b.

It also conflicts with the plan for automatic iteration depth (2.3), which would change the iteration count regularly. As it stands, each change would recompute the whole ancestor chain.

Suggested fixes:
- Keep the old-iteration records as display-only fallback, since they look almost identical, and replace them as new tiles arrive.
- Design raising the iteration limit as **extending** existing tiles. The resumable kernel already has the machinery: keep orbit state for pixels that hit the limit (or just their coordinates), and resume only those. Escaped samples stay valid. Store the iteration limit in `TileRecord`.

### 3. A failing tile is retried every frame (`TileStore.swift:91`, `:318`)
When a tile fails, the worker sets `suspended = true`. But `update()` sets `suspended = false` at the start of every frame, and `failed` is never added to any more (the `failed.insert` from 2.1a is gone). A persistent failure, such as a texture allocation failing under memory pressure on the iPhone 11 Pro, is therefore retried at display rate. Each retry tries to allocate two 258² textures and a 1 MiB buffer.

Fix: record failures per key with backoff, and add a headless test that injects an allocation failure.

### 4. The ProMotion key is still missing (build settings)
Add `INFOPLIST_KEY_CADisableMinimumFrameDurationOnPhone = YES` to the app target's Debug and Release configurations. Without it, iPhones cap `MTKView` and `CADisplayLink` at 60 Hz, whatever `preferredFramesPerSecond` says. Correct `Performance.md:210–211`.

### 5. Draw only when something changes (`GPUCanvas`)
Pausing when the scene is inactive is done. The remaining part is to stop drawing when active but idle:
- set `enableSetNeedsDisplay = true`;
- keep the view unpaused only while there's a reason: a gesture or inertia, a fade in progress, a newly arrived tile, or pending work.

Note that inertia is currently advanced inside `draw(in:)`. On-demand drawing therefore has to keep requesting frames while `motion.active` is true. The per-frame `tiles.update` (see finding 6) also depends on continuous drawing.

### 6. Per-frame CPU work on the main thread (`TileStore.update`)
Every frame rebuilds the ancestor `Set`, walks `needed` to update LRU times, and calls `evict(reserving:)`, which sorts every record that isn't needed. It's cheap on the M1 Pro at today's sizes. At 120 Hz on an iPhone, with a full cache, it's a steady stream of allocations on the main thread.

Fix: return early when the viewport, size and settings haven't changed, and measure `update` time in the HUD on the iPhone 11 Pro.

### 7. Cache the palette texture (`GPUContext.paletteTexture`)
Build the 1D palette texture once per `Palette` and reuse it. Recolouring allocates a fresh texture and re-uploads the table once per tile.

### 8. No golden test covers the product's output
The goldens test the legacy full-frame renderers. The tiles only have integration checks (`tiles-deep.png` was checked by eye). Adopt the pixel-centre mapping everywhere, re-record the fixtures on purpose, then add a golden for the tile compositor. Once the conventions match, this can also compare against the CPU Double reference.

### 9. Commit a formatter configuration
Add a `.swift-format` file and a `make format` target, and run it once across the remaining dense files. Otherwise the style will drift back as agents write new code.

### 10. Minor
- The 2.1c commit message has no `2.1c:` prefix, unlike its neighbours.
- A parent mipmap's gutter still comes from direct sampling while its interior is averaged, so a faint 1-texel seam may be visible when zoomed out. It's documented; check it by eye.
- `UIScreen.main` is deprecated. Take the screen from the view's window instead.

## Notes per commit

### `2344a77` Plan: max-iteration heuristic *(Claude's commit)*
It swept the user's `.gitignore` and `project.pbxproj` changes into a `plan.md` commit via `git commit -am`. Those changes are correct: iOS 18 as the minimum, visionOS removed. The commit message is misleading, but the branch is unpushed. Agents now stage explicit paths only.

### `a166385` 1.2: strict-math cost
A good record of the 8–11% cost to the Float kernel. Deferring the fix for the per-pixel division was the right call, and 1.4 delivered it. One option for later: compile the Float kernel with fast math in its own library.

### `5471b3d` 1.3: goldens and `make test`
The fixture design is sound: a data manifest, deliberate re-recording, exact matches for CPU renderers, and a guard against images with no detail. Tolerances should be tightened to just above the measured mismatch rates. The `baseSpan: 0` trick for single points should become a helper.

### `20481de` 1.6: refactor
A good decomposition: `Viewport`, `RendererID`, a single command table, and separate views. `RendererRegistry` is a protocol with only one implementation; a `switch` would do. `Implementation.md` and `plan.md` now both record progress, so pick one as the source of truth.

### `00cc5ad` 1.4: GPU pipeline
The pipeline stays on the GPU end to end and the benchmarks are clear. The follow-ups I raised (the polling loop, dead code) have since been resolved. The full-frame path is now used only for the CLI and lab, where two command buffers per render doesn't matter.

### `8c460b1` 1.5: smooth colouring and palettes
Excellent work, and the independent Python smooth-count check is the standout test. Still to do: cache the palette texture (finding 7) and decide how smooth counts will be stored before perturbation.

### `e2d3747` 1.7: developer panel
It meets the plan. The ⌥-reveal menu that rebuilds the menu bar is fragile; an alternate menu item, or just the defaults flag, is more conventional. On a Mac, `uname().machine` returns "arm64"; use `hw.model`. The kernel-only benchmark report still says it "includes colour conversion".

### `ba7aa35` 1.8: native navigation
The exact inertia solution with a 60/120 Hz invariance test is a real craft detail, and the native gesture handling is right. The frame-rate claim in the docs is wrong (finding 4). `MacInputView.keyDown` duplicates the command table.

### `3d6a26b` 2.1a: fixed-level tiles
The foundations are right: anchor-relative keys, a gutter with pixel-centre sampling, cancellation, and an all-at-once palette swap. The small-batch throughput problem has since been reworked in 2.1d.

### `d8124e0` 2.1b: multiple levels with parent fallback
This is the core of smooth zooming, and it's clean:
- `bestAvailable` walks up the tile's ancestors, then checks retained old-generation tiles by their bounds in the complex plane.
- Rebasing at index 2³⁰ keeps the previous coverage on screen.
- The magenta test for uncovered pixels is exactly the right test.

The switch to `ceil(lod)` with coarse-first ordering is sound for continuous zooming (see finding 1 for jumps). Keeping *all* old records as fallback here was the better policy; 2.1d narrowed it (finding 2).

### `975f832` 2.1c: blending levels and fading in
Blending three coloured sources (coarse, base, fine) weighted by fractional level and fade time implements the "blend after colouring" rule from `plan.md` exactly. The shader comment says so, and a real GPU render with known colours tests the weights. The tile-border and level-digit overlay drawn in the shader is a nice debugging tool that costs nothing when it's off. `TilePresentation` is correctly pure and unit-tested.

A small point: the fine level fades in over 125 ms from its ready time even when the base tile underneath arrived in the same frame, so a cold start fades in twice. That's acceptable.

### `bd79b39` 2.1d: mipmaps, bounded refinement, budgeted cache
This is the largest commit and the most impressive:
- Resumable batches with per-pixel orbit state, verified byte-for-byte against the one-shot kernel for both precisions.
- Exact 2×2 colour mipmaps, verified against a CPU box average for every pixel.
- A byte-accurate LRU budget per device that protects visible tiles and their ancestors, and lowers resolution rather than evicting what's needed.
- Prefetching in the direction of zoom that doesn't cause eviction churn.
- Scene-lifecycle cancellation, and an honest `Architecture.md`.

Concerns:
- Findings 1, 2, 3, 5 and 6.
- **The commit is too big to review properly:** about 1,600 lines changed across 16 files, mixing a reformat with behaviour changes. Next time, commit the formatter pass separately.
- **Transient memory during a palette change:** replacement textures are allocated for every record plus the fallback before the swap. With the iOS budget, that's about 50 MB of extra allocations at once. It fits inside the reserved third, but it's worth watching on the 4 GB iPhone 11 Pro.
